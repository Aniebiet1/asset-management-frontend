Executive summary

TecresTrackIT AMS was designed security-first. It is a from-scratch platform built specifically to prevent the classes of weakness most common in multi-tenant business software: data leaking between customers, accounts protected only by a password, long-lived sessions, and permissions enforced only in the user interface.

Independent verification

The controls in this report were tested by attacking them directly: 34 automated attack scenarios run against the real application and database, plus 7 live tests against a running server, following OWASP methodology. Every attempt to read or change another customer's data, forge or tamper with a session token, skip two-factor authentication, escalate a role, or inject SQL was blocked. One vulnerability found during testing was fixed immediately and re-verified with a permanent regression test (section 11). Further hardening items identified by the assessment are tracked to closure in Tecres' internal remediation register.

Security architecture at a glance

TecresTrackIT follows a defense-in-depth design: every request crosses several independent layers, and each one would still protect data if another failed. The web application is treated as untrusted; all enforcement happens on the server.

1 · Transport: HTTPS only, HSTS for one year, strict CORS allow-list
2 · Edge protection: security headers (CSP, anti-framing, no-sniff), request-size limits, rate limiting per IP and per account
3 · Authentication: signed, purpose-bound, 15-minute tokens; mandatory two-factor sign-in
4 · Organization context: the customer is taken from the verified token; suspended customers are refused on every request
5 · Authorization: role permission check on every action
6 · Input validation: every field checked against a strict schema; unknown fields discarded
7 · Data access: org-scoped query layer; ownership re-checked on direct lookups and file downloads
8 · Data at rest: argon2id passwords, AES-256-GCM secrets, hashed tokens
9 · Observability: activity and security logs, automated alerts, platform risk dashboard

Two identity systems, fully separated

Customer users and Tecres staff are kept apart at every level. They live in different database tables, have different roles, sign in at different addresses, and hold tokens signed with different secret keys. A customer's token is mathematically incapable of opening the Tecres console, and a Tecres token cannot act inside a customer's workspace.

Customer users
Roles: super admin, admin, asset manager, staff

Tecres platform admins

Workspaces are provisioned, never self-registered

Customer workspaces are created by Tecres platform owners only, together with their first administrator. Further staff join by invitation from their own administrator. This keeps every organization on the platform a known, contracted customer.

Security, engineering

Identity and authentication

3.1 Password security

  • Passwords are hashed with argon2id, the algorithm recommended by OWASP and winner of the Password Hashing Competition. It is deliberately slow and memory-hard, which makes offline guessing expensive even if a database were ever copied.
  • Passwords are never stored, logged or returned in plain text, and every API response that includes a user removes the hash.
  • Every sign-in failure (unknown email, wrong password, inactive or locked account) returns the identical message "Invalid email or password", so the sign-in form does not reveal which part was wrong.

3.2 Mandatory two-factor authentication

Every account, customer and Tecres alike, must use an authenticator app (Google Authenticator, Microsoft Authenticator, 1Password and similar). There is no setting to turn it off for an organization and no way to reach a working session without it. A correct password earns only a short-lived, single-purpose token that can do nothing except be exchanged for a session when the 6-digit code is entered.

3.4 Password reset

  • The reset form responds identically whether or not the email exists.
  • Reset links are random 256-bit tokens, stored only as hashes, valid for 60 minutes and usable once.
  • Completing a reset signs the account out of every device.

4.1 Purpose-bound tokens

Every token states what it is for (its audience), and every check accepts exactly one purpose. A token earned by the password step can therefore never be used as a session, a customer token can never be used on the Tecres console, and the reverse is equally impossible.

Token purposes · backend/src/lib/jwt.ts
const AUDIENCE = {
  access: "tecres:tenant:access",
  preAuth: "tecres:tenant:pre-auth",
  platformAccess: "tecres:platform:access",
  platformPreAuth: "tecres:platform:pre-auth",
} as const;

export function verifyAccessToken(token: string) {
  return jwt.verify(token, env.JWT_ACCESS_SECRET, { audience: AUDIENCE.access });
}

4.2 Rotation and stolen-token detection

Each time the application renews a session, the old refresh token is retired and a new one issued. If a retired token is ever presented again, it can only mean someone copied it. The platform then revokes the entire session chain, signing out both the attacker and the real user, who simply signs in again.

Theft detection · backend/src/modules/auth/auth.service.ts
if (existing.revokedAt) {
  // Reuse of a revoked token is a theft signal: revoke the entire rotation family.
  await db.update(refreshTokens).set({ revokedAt: new Date() })
    .where(and(eq(refreshTokens.familyId, existing.familyId), isNull(refreshTokens.revokedAt)));
  throw new UnauthorizedError("Refresh token reuse detected, session revoked");
}

4.3 Ending sessions

  • Sign out revokes the current session; sign out everywhere revokes every session of the account.
  • A password reset, or a reset forced by Tecres, revokes all sessions immediately.
  • Suspending an organization blocks all of its users on their very next request.

Authorization and access control

Permissions are enforced by the server on every request through a single authorize() check tied to a central permission matrix. The web application hides buttons a role cannot use, purely for convenience; calling the API directly gives exactly the same answer as the screen.

Enforcement point · backend/src/middleware/authorize.ts
export function authorize(permission: keyof PermissionSet) {
  return (req, _res, next) => {
    if (!req.user) throw new UnauthorizedError();
    if (!hasPermission(req.user.role, permission)) throw new ForbiddenError(`Missing required permission: ${permission}`);
    next();
  };
}

5.2 Financial data is removed, not hidden

For roles without valuation rights, monetary fields are deleted from the server's response before it leaves the API. They are not blanked in the browser; they are never sent. Inspecting network traffic reveals nothing more than the screen shows.

backend/src/lib/permissions.ts
export const VALUATION_FIELDS = ["purchasePrice", "currentValue", "salvageValue", "totalValuation"] as const;

export function stripValuationFields(obj, role) {
  if (hasPermission(role, "canViewAssetValuation")) return obj;
  const clone = { ...obj };
  for (const field of VALUATION_FIELDS) delete clone[field];
  return clone;
}

5.3 Segregation of duties

Asset audits follow a controlled workflow (draft, assigned, in progress, submitted, verified). The person who verifies an audit can never be the person who submitted it, whatever their role. This is enforced in the server's audit service, and every status change is permanently recorded with who made it.

Security, engineering

Tenant isolation

All customers share one database, so keeping each organization's data separate is the platform's most important property. Isolation is built into the structure of the code rather than left to careful coding.

6.1 Three rules, enforced structurally

  1. The organization comes only from the signed token. No customer-facing endpoint accepts an organization ID from the request. A value smuggled into a request is discarded, and editing a token breaks its signature.
  2. Every query is bound to one organization. Customer data is read and written through scopedDb(orgId), whose every operation adds the organization filter. There is no function in it that omits the filter, so an unscoped query cannot be written by accident.
  3. Ownership is re-checked on direct access. Looking up any record or file by its ID confirms it belongs to the caller's organization. A record from another organization answers "not found", so its existence is not even confirmed.
Org-scoped data access · backend/src/lib/scopedDb.ts
export function scopedDb(orgId: string) {
  return {
    findById(table, id) {
      return db.select().from(table)
        .where(and(eq(table.orgId, orgId), eq(table.id, id)))   // the org filter is not optional
        .then((rows) => rows[0]);
    },
    insert(table, data) {
      return db.insert(table).values({ ...data, orgId }).returning();   // orgId always injected
    },
    // findMany, update, remove: same pattern
  };
}
File downloads re-check ownership · backend/src/modules/files/files.router.ts
const meta = await getFileMeta(req.params.id);
if (!meta) throw new NotFoundError("File not found");
if (meta.orgId !== req.user!.orgId) throw new NotFoundError("File not found");

6.2 Organization status on every request

Before any customer request is processed, the organization named in the token is loaded and checked. A suspended organization is refused immediately, even if its users hold tokens that have not yet expired.

Verified by attack

Penetration tests tried to read, edit and delete another organization's assets by ID, download another organization's files, inject a foreign organization ID, swap the organization inside a token, and search across organizations. Every attempt was blocked (tests PT-03, PT-19, PT-20, PT-21, PT-28 and the core isolation test).

Encryption of authenticator secrets · backend/src/lib/crypto.ts
export function encryptSecret(plaintext: string): string {
  const iv = crypto.randomBytes(12);
  const cipher = crypto.createCipheriv("aes-256-gcm", ENCRYPTION_KEY, iv);
  const encrypted = Buffer.concat([cipher.update(plaintext, "utf8"), cipher.final()]);
  return [iv, cipher.getAuthTag(), encrypted].map((b) => b.toString("hex")).join(".");
}

7.2 Data in transit

  • HTTPS is required; HSTS instructs browsers to refuse plain HTTP for one year, including subdomains.
  • Session cookies carry Secure, httpOnly and a path restricted to the sign-in endpoints.
  • Only the Tecres web application's own address may call the API from a browser (CORS allow-list).

7.3 Secrets management

Signing and encryption keys live in the server environment, never in source code. At start-up every key is validated: the server refuses to run if any is missing or shorter than 32 characters. Customer and Tecres tokens are signed with different keys.

7.4 Data minimization

  • Financial values are withheld from roles that do not need them (section 5.2).
  • The public sign-in page can learn only a workspace's name, logo and color, never its data.
  • Expired tokens and invitations are deleted automatically every hour.

Application and API hardening

8.1 Strict input validation

Every request body, query string and URL parameter is checked against a Zod schema before any business logic runs. Values of the wrong type or format are rejected, and fields the schema does not name are discarded, which prevents mass-assignment attacks. Database access uses parameterized queries through the Drizzle ORM, and user-selectable sort columns map to a fixed list, so user input is never assembled into SQL text.

Example schema · backend/src/modules/people/people.schema.ts
export const personUpdateSchema = z.object({
  name: z.string().min(1).max(255).optional(),
  role: z.enum(["super_admin", "admin", "asset_manager", "staff"]).optional(),
  isActive: z.boolean().optional(),
  // anything else in the request body is dropped
});

8.3 Safe error handling

Clients receive only an error code and a plain message. Stack traces, file paths and database details are written to the server log and never returned. A record belonging to another organization is reported as "not found" rather than "forbidden".

8.4 Resource limits

Request bodies are capped at 2 MB, file uploads at 20 MB and logos at 5 MB (images only), alongside the rate limits in section 3.3.

8.5 Browser-side safeguards

  • Access tokens are kept in memory only, never in localStorage or sessionStorage.
  • The customer application and the Tecres console use separate stores and API clients, so a token can never flow from one to the other.
  • Concurrent session renewals are merged into one, so the application never trips its own stolen-token detection.

Secure development practices

  • Security by structure. The safe way is the easy way: org-scoped data access, a shared CRUD factory that includes permission checks, typed errors, and validation middleware on every route.
  • Typed end to end. TypeScript on both sides; changes must pass a strict type-check and production build before they are considered done.
  • Security regression tests. Authentication, isolation, token handling and the audit workflow are covered by integration tests against a real database, and every penetration test in section 11 is kept as a repeatable test, so a fixed weakness cannot quietly return.
  • Mandatory testing for sensitive changes. Any change to authentication, org-scoped queries, tokens or audits must run the full integration and security suites.
  • Dependency auditing of both applications' production dependencies as part of security review.
  • No secrets in code. Keys come only from the validated environment.

11.6 Found and fixed during testing

Testing identified that the short-lived token issued after the password step was accepted by the Tecres console as if sign-in had completed, which could have let someone holding a Tecres staff password view console pages without the authenticator code. It was fixed during the engagement by binding every token to a single purpose (section 4.1), re-tested (the attack now returns HTTP 401 on every route), and kept as a permanent regression test (tokenPurpose.security.test.ts).

11.7 Conclusion

Result

With the fix described in 11.6 in place, every attempt to access another customer's data, forge or tamper with tokens, bypass two-factor authentication, escalate privileges or inject SQL was blocked. The penetration test confirms that TecresTrackIT's core protections (mandatory two-factor authentication, purpose-bound short-lived sessions with theft detection, server-side authorization and structural tenant isolation) hold up against direct attack. Additional hardening opportunities identified by the assessment are tracked to closure in Tecres' internal remediation register and are re-verified by the same test suite.
