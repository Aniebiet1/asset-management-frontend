Overview and stack

TecresTrackIT AMS is a multi-tenant IT asset management platform. Customer organizations (tenants) track their assets through check-out, maintenance, audits, reporting and labelling. Tecres staff run the service from a separate platform console.

The system is two applications in two repositories that talk over a JSON API:

LayerRepositoryTechnology
Frontend SPAasset-management-frontendVite, React 19, TypeScript, React Router 7, TanStack Query (server state), Zustand (client state), Tailwind CSS v4, shadcn/ui (Nova preset, Radix primitives), react-hook-form + zod, recharts, jspdf, xlsx, jsbarcode, qrcode, html5-qrcode. Package manager: npm.
Backend APIasset-management-backendNode 20+, Express 4, TypeScript, Drizzle ORM on PostgreSQL, Zod, argon2, jsonwebtoken, otplib, Helmet, express-rate-limit, pino, nodemailer / Brevo, Cloudinary, AWS S3. Package manager: pnpm.
Databasen/aPostgreSQL, one database shared by all tenants; every tenant table carries org_id.
Browser: React SPA; tenant app at /, platform console at /platform/*
HTTPS JSON API: /api/*, bearer access token + httpOnly refresh cookie
Express middleware chain: helmet, CORS, logging, rate limit, body parsing
Module routers: authenticate → loadOrgContext → authorize → validate → service
Services + Drizzle: business logic, scopedDb(orgId)
PostgreSQL · Cloudinary / S3 (files) · Brevo (email)

Design principles

  • The server is the only security boundary. The frontend hides what a role cannot use, but every rule is enforced again in the API.
  • Tenant isolation is structural. The organization comes from the verified token, never from the request, and queries go through an org-scoped helper.
  • Two identities, never mixed. Tenant users and Tecres platform admins have separate tables, secrets, middleware, stores and API clients.
  • Mandatory two-factor authentication for every account, before any session exists.
  • Workspaces are provisioned by Tecres. There is no public sign-up; a platform admin creates an organization and its first super admin.

Authentication and sessions

5.1 Sign-in sequence

#CallResult
1POST /api/auth/login
{ email, password }		Finds the user by email (which identifies the org), checks lockout, verifies argon2id. First sign-in: { status: "totp_enrollment_required", enrollmentToken }. Otherwise { status: "totp_challenge_required", preAuthToken }. All failures: 401 "Invalid email or password".
2aPOST /api/auth/totp/enroll
{ enrollmentToken }		Creates a pending encrypted secret; returns QR code data URL and manual key
2bPOST /api/auth/totp/verify-enroll
{ enrollmentToken, code }		Activates TOTP, issues 10 recovery codes and a session
3POST /api/auth/login/totp
{ preAuthToken, code }		Verifies the code (or a recovery code), stamps last_used_step, issues a session
4POST /api/auth/refresh (cookie)Rotates the refresh token; returns a new access token

A session is a 15-minute access JWT (returned in the body, kept in memory by the SPA) plus a 30-day opaque refresh token in an httpOnly cookie scoped to /api/auth.

Each verifier accepts exactly one audience. A new token type must get its own audience constant in src/lib/jwt.ts; reusing one lets a token be accepted where it was never meant to be (see the Security Remediation Register, item F-01).

5.4 Password reset and forced reset

  • POST /auth/password-reset/request always answers 200 with the same message (no account discovery), and emails a 60-minute single-use link to the user.
  • POST /auth/password-reset/confirm sets the new password and revokes every refresh token.
  • A platform owner can force a reset (POST /platform/orgs/:id/users/:userId/force-reset): sessions are revoked immediately and the user is emailed a reset link.

5.5 Platform admin authentication

Same two-step shape under /api/platform/auth/*, but platform sessions are a single 15-minute JWT with no refresh endpoint: a reload or expiry means signing in again. New platform admins join by invitation (POST /platform/admins/invite → emailed link → POST /platform/admins/invite/:token/accept sets a password, then TOTP enrollment).

Multi-tenancy and authorization

6.1 Org scoping

All tenants share one database. Three rules keep them apart; break none of them:

  1. orgId comes only from req.user.orgId (the verified token). No tenant route accepts it from the body, query or params.
  2. Tenant data access goes through scopedDb(orgId) wherever the resource fits its shape, so the org filter cannot be forgotten.
  3. A lookup by ID in another org returns 404, not 403, so IDs of other tenants' records are not confirmed to exist.
Using scopedDb · any tenant service
const scoped = scopedDb(orgId);
const location = await scoped.findById(locations, id);        // WHERE org_id = $1 AND id = $2
if (!location) throw new NotFoundError();
await scoped.update(locations, id, { name, updatedAt: new Date() });
await scoped.insert(departments, { id: generateId(), name });  // orgId injected automatically

6.2 Simple CRUD resources

Catalog-style resources use createCrudRouter(), which wires list/get/create/update/delete through scopedDb, maps unique violations to 409, and lets any org member read while requiring a permission to write:

  table: locations,
  createSchema: locationCreateSchema,

Domain workflows

7.1 Workspace provisioning

Platform ownerPOST /platform/orgs
→
Org + first super admincreated in one call
→
First sign-inTOTP enrollment

Onboarding wizardprofile, branding, catalog
→
Workspace liveonboarding-complete

The platform admin sets the first admin's credentials and hands them over out of band. Until onboarding_completed_at is set, the SPA routes that admin to /onboarding. Further staff join through POST /people/invite (emailed link, user sets their own password) or are added directly by an admin with POST /people.

7.2 Structured asset tags

When an organization has at least one subsidiary configured, new asset tags are generated server-side:

{SUB}-{TYPE}-{BRANCH}-{DDMMYY}-{index}[-{suffix}]        e.g. CCL-FF-09-210824-004
// index : running counter per asset type across the whole org (asset_tag_sequences)
// suffix: A, B, C... only when staff mark the asset as a duplicate of an existing one

Once set, tag-driving fields are locked on PUT /assets/:id. Corrections go through PATCH /assets/:id/identity (canEditAssetIdentity), which regenerates the tag and writes an activity-log entry. GET /asset-tags/preview returns an advisory preview for the form. Organizations without subsidiaries keep a free-text tag.

7.3 Check-out and return

POST /assignments/checkout (assetId, userId, optional expectedReturnDate, conditionOut, notes) sets the asset to in_use; POST /assignments/checkin (assignmentId, conditionIn, optional notes) returns it to available. GET /assignments/:id/receipt supplies data for the PDF receipt the frontend renders with jspdf.

7.4 Maintenance

Moving a record to in_progress sets the asset to in_maintenance; completed or cancelled returns it to available. Staff may schedule maintenance; updating or completing a record needs canCompleteMaintenance.

8.2 Sessions in the browser

  • Tokens live in memory (Zustand), never localStorage. On boot, auth.store.bootstrap() calls /auth/refresh using the httpOnly cookie to restore the session.
  • apiFetch attaches the bearer token and, on a 401, performs one refresh and retries. Concurrent refreshes are de-duplicated into a single in-flight promise, because the backend treats a second use of a rotated token as theft.
  • The platform console uses platformApiFetch and platformAuth.store.ts. A 401 there simply signs the admin out (no refresh endpoint). Never share a store, token or client between the two identities.
Tenant API client · src/lib/api-client.ts
export async function apiFetch<T>(path: string, init: RequestInit = {}): Promise<T> {
  let res = await doFetch(path, init);
  if (res.status === 401) {
    const restored = await useAuthStore.getState().refresh();   // de-duplicated
    if (restored) res = await doFetch(path, init);
    else { useAuthStore.getState().clearSession(); throw new ApiError(401, "UNAUTHORIZED", "Your session has expired."); }
  }
  if (!res.ok) throw await ApiError.fromResponse(res);
  return res.status === 204 ? (undefined as T) : res.json();
}

8.3 Server state with TanStack Query

Each feature owns an api.ts of query and mutation hooks. Mutations invalidate every query key they can affect.

src/features/maintenance/api.ts (abridged)
export function useMaintenanceQuery() {
  return useQuery({
    queryKey: ["maintenance"],
    queryFn: () => apiFetch<{ data: MaintenanceRecord[] }>("/maintenance").then((r) => r.data),
  });
}

export function useUpdateMaintenanceMutation() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: ({ id, input }) => apiFetch(`/maintenance/${id}`, { method: "PUT", body: JSON.stringify(input) }),
    // status changes also flip the asset's status, so refresh both
    onSuccess: () => { queryClient.invalidateQueries({ queryKey: ["maintenance"] });
                       queryClient.invalidateQueries({ queryKey: ["assets"] }); },
  });
}

8.4 Theming and per-organization branding

src/index.css defines --org-primary and --org-accent as the only two colors that vary per tenant; every other token (--primary, --ring, sidebar, charts) derives from them. useThemeStore().applyOrgTheme(org) is the single place that writes them to the document. Light and dark palettes are both fully defined: the theme follows the device until the user picks one in the header, which is saved to localStorage.tecres_theme (a preference, not a secret). The sign-in page looks up the workspace from the email as it is typed and shows that organization's logo and color before sign-in.

8.5 UI conventions

  • shadcn/ui components are added with npx shadcn@latest add <name> into src/components/ui; class merging uses the cn package; Radix comes from the unified radix-ui package.
  • No em dashes in any user-visible text; use "-" for empty values.
  • Reports, receipts and labels are rendered client-side (jspdf, xlsx, jsbarcode, qrcode); the backend returns JSON only.

Email

src/lib/email.ts sends through the Brevo HTTPS API when BREVO_API_KEY is set (cloud hosts block SMTP ports), otherwise through SMTP when configured, otherwise it logs a warning and sends nothing. Templates are plain HTML in src/emails/templates/ with {{var}} placeholders, wrapped by layout.html and carrying the organization's logo and color where relevant.

src/lib/storage.ts stores images on Cloudinary when configured, other files on S3 when configured, and falls back to PostgreSQL bytea. Every file row records its org_id, and GET /files/:id re-checks it on download.

Backend environment variables

Validated by Zod in src/config/env.ts; the process refuses to start if a required value is missing or a secret is under 32 characters.

VariablePurpose
DATABASE_URLPostgreSQL connection string (required)
JWT_ACCESS_SECRETSigns tenant access and pre-auth tokens
JWT_REFRESH_SECRETRequired at start-up but currently unused (refresh tokens are opaque random values, not JWTs)
PLATFORM_ADMIN_JWT_SECRETSigns platform tokens; must differ from the tenant secret
TOTP_ENCRYPTION_KEYEncrypts TOTP secrets at rest. Changing it makes every enrolled authenticator unusable.
CORS_ALLOWED_ORIGINSComma-separated frontend origins; the first is also used to build emailed links
COOKIE_DOMAINDomain for the refresh cookie
TRUST_PROXYNumber of reverse proxies in front (defaults to 1 in production). Setting it higher than reality lets clients spoof their IP past rate limits.
BREVO_API_KEY, SMTP_*Email transport (optional in development)
CLOUDINARY_*, AWS_*File storage (optional; falls back to the database)
NODE_ENV, PORTProduction turns on Secure; SameSite=None cookies and proxy trust

Production notes

  • pnpm build compiles TypeScript and copies email templates and migrations into dist/; pnpm start applies migrations, then starts the server.
  • The frontend is a static build (npm run build → dist/) served from app.tecrestrackit.com; it needs VITE_API_BASE_URL at build time.
  • Because frontend and API are on different sites in production, the refresh cookie is SameSite=None; Secure, and the API's CORS_ALLOWED_ORIGINS must list the exact frontend origin.

The backend suites run against the real Express app and a real PostgreSQL database, not mocks:

  • auth.integration.test.ts: login, TOTP, refresh rotation and reuse detection, cross-org isolation, valuation hiding, global email uniqueness.
  • tokenPurpose.security.test.ts: pre-auth tokens can never act as sessions.
  • test/security/pentest.security.test.ts: 32 attack scenarios; open hardening items are recorded with it.fails (see the Security Remediation Register).
When you must run the backend tests

Any change to authentication, an org-scoped query, token handling or the audit state machine. These are exactly the bug classes the backend was rebuilt to prevent.

Playwright is not a project dependency. Install it with npm install --no-save playwright for one-off checks, and confirm git diff package.json package-lock.json is empty before committing.

Conventions for contributors

Backend

  • Each module is <name>.router.ts (HTTP wiring only) + <name>.service.ts (logic and database) + <name>.schema.ts (Zod).
  • Every request body, query and params goes through validate(); never read raw req.body.
  • Never accept orgId from a client. Use scopedDb(orgId) where it fits, and createCrudRouter() for plain catalog resources.
  • Platform routes use only authenticatePlatformAdmin/authorizePlatformAdmin; tenant routes only authenticate/authorize. No route accepts both.
  • New money fields go in VALUATION_FIELDS and through stripValuationFields().
  • Throw the typed errors from src/lib/errors.ts (NotFoundError, ForbiddenError, ConflictError, ...) rather than writing responses by hand.

Frontend

  • One folder per domain in src/features, with an api.ts of TanStack Query hooks; invalidate every affected key after a mutation.
  • Keep types in src/types in step with the backend schema by hand.
  • Route per-organization colors only through --org-primary/--org-accent and applyOrgTheme; support both light and dark palettes.
  • Package managers: npm for the frontend, pnpm for the backend.

Before calling a change done

  1. Backend: pnpm typecheck clean; pnpm test if you touched auth, scoping, tokens or audits.
  2. Frontend: npx tsc -b clean and npm run build succeeds.
  3. If a page renders real data, smoke-test it in a browser and check the console.
  4. Update BUILD_PLAN.md's status table if you started or finished a phase.
